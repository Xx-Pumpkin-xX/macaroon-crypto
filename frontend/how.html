How it works

Five steps, from the moment a file leaves your browser to the moment a link stops working.

  1. The file is encrypted before it leaves the browser

    The page makes a random 256-bit key k and encrypts the file name and text with AES-256-GCM. The server stores one opaque blob and never sees k, so it cannot read the file. The tag at the end means any change to the blob is detected when it is decrypted.

  2. A link carries three things

    Everything after # stays in the browser: browsers do not send the fragment to the server. The page sends f in the request path and t in a header, and keeps k to itself.

    localhost:8000/view.html#f=q3J8xY2mN0aPz7Lk1VbC4w&t=MDAyMWxvY2…dmZjQK&k=Rk9xS1d3…

    • f file ID: picks the file. Sent in the path.
    • t token: what this link may do. Sent in the Authorization header.
    • k file key: decrypts the file. Never sent.

  3. The token is a chain of HMACs

    Only the first signature needs the server's root key. Each caveat after it is chained with HMAC(previous signature, caveat), so anyone holding a token can add a caveat, but removing one would mean running HMAC backwards. Add caveats, then strip one. This sandbox uses a throwaway key made in your browser, not the server's.

    1. The server checks every request in a fixed order

      The first check that fails decides the answer. 401 means the token is not genuine; 403 means it is genuine but does not allow this.

      1. Was a token sent?401 missing_token
      2. Does the file still exist?404 not_found
      3. Does the HMAC chain, rebuilt from the root key, give the same signature? Are all caveats known, and at most 20?401 invalid_token
      4. Is the earliest expiry still in the future?403 expired
      5. Is no share_id in the token revoked?403 revoked
      6. Does the lowest op allow this action?403 forbidden
      7. All passed200 or 204

    2. Revoking a share cuts off everything made from it

      Every share gets a random share_id caveat, and links made from it inherit that caveat. Revoking S1 blocks B, and C, who got a link through B. D's link came from a separate share, so it keeps working. The network map shows this against the real server.
